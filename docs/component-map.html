MESA Case 03 · Aangan Studio, Pune

The call agent that won't quote

Every phone enquiry answered, qualified against Nikhil's own rubric, and booked during the call. It never gives a price. That one refusal is designed in three times over, because a prompt is a request and not a guarantee.

The Cut

Quoting per-sq-ft pricing — the one thing Nikhil asked for and did not get

"Your designer will walk you through pricing on the consultation, because it depends on your site and your choices."

A price said in the studio's voice is heard as a commitment, and it cannot be taken back. A wrong classification costs a callback; a wrong price costs the relationship. So pricing is not delegated at all — and it is blocked at three separate layers, on the assumption that any one of them can fail.

  1. The rate card is never in the room. Only the rubric and the services file are ever loaded. The loader refuses to start if pricing.md appears, and that check runs ahead of the cache so a rate card cannot ride along on a warm serverless instance.
  2. The output is filtered in code. Rupee amounts, lakh and crore figures, per-sq-ft rates and estimate language are stripped from every free-text field before a human sees them. Measurements survive: 1,400 sq ft and six weeks are not money.
  3. Asking can never disqualify. The rubric says so explicitly, so a not_fit that cites pricing with no volunteered budget is overruled in code and the override recorded on the row.

After hours

Of 20 calls — including a 10:47pm missed call with no voicemail

The twenty verdicts turn on seven different criteria, which is the part worth checking: service area for Nashik, timeline for the caller who wanted it done before Diwali, a volunteered budget far below scope, an existing client's complaint, a missed call with nothing to assess. Two callers pressed for a price. Both qualified, and the filter stripped a figure from each — which is exactly where a careless build gets it backwards.

What the real calls corrected

Vaani sends no call id

The first live call reached the webhook twice and was dropped both times. The documented call_id is absent from what it actually posts; the stable identifier is room_name, because Vaani runs on LiveKit. There is no event field either, so the event is now inferred from the payload's shape.

[webhook] no call id in payload; keys were: room_name,phone_number,call_type,agent_name

call_duration is seconds, not milliseconds

A 208-second call was stored as zero. Dividing by a thousand rounded it away and took the cost column with it. Start and end timestamps are unambiguous, so they decide now; the reported duration is a fallback whose unit is inferred from magnitude.

A probe is not a failure

Answering a connectivity test with 4xx is how a provider decides an endpoint is broken and disables the hook. Anything unrecognised now gets a 200 with the diagnosis in the body. A bad token is still rejected outright.
